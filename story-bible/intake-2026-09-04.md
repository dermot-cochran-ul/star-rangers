## Third, same session — does church-space still need to be private?

Dermot, verbatim:

> does church-space still need to be private if it is clearly its own edition?

A question, not a direction, and answered in chat as an assessment. Recorded
here because it is undecided and because the answer is an engine change if he
wants one.

### What privacy does today that the ladder does not

`private: true` on the `church-space` thread (`lib/storyline-threads.js`)
hides it on **every build that does not name it in** — including the
unfiltered canonical site, GitHub Pages, local dev, and every third-party
fork, all of which resolve the default edition and carry no `THREADS` filter.
The tier ladder (`lib/editions.js`, 3 September) decides only what the
**branded** editions carry; it says nothing about an unfiltered build. So
today two mechanisms together produce "only the contemplative editions show
Church Space": the ladder puts the thread in `CONTEMPLATIVE_TIER`, and
privacy keeps it off the default build. Dropping privacy with nothing in its
place would put Season 8 on fianilchruinne.com, which the 3 September ruling
placed at the general tier on purpose.

Privacy also carries three pieces of special machinery: `homeDomain` (where
an excluded placeholder points, since the canonical site excludes the thread
too), `signatureTags` (the validator's guard against a church-space page
shipping untagged on a public domain), and the **public → private link
boundary** in `validate-content.js`, which refused the Reading Tiers page's
link to the thread's landing page the same morning — so the page names Church
Space in plain text.

### Three shapes, put as choices

1. **Keep it as it is.** Privacy and the ladder overlap but do not conflict;
   nothing is broken. Cost: two concepts where one would do, and the
   link-boundary rule keeps biting reader-facing pages that want to point at
   the contemplative tier.
2. **Replace privacy with tier gating.** Give the thread `tier:
   "contemplative"` and have `content-filter.js` hide any thread above the
   build's tier — the mechanism the `::: pov … tier=contemplative` blocks
   already use. Same visible outcome today (the two contemplative editions
   and the archive show it; the default edition is general, so the canonical
   site, GitHub Pages and every fork still do not). What retires: `private`
   as a concept, `homeDomain` (the placeholder can point at the tier's
   ranking host), the signature-tag check (membership by season and tag is
   unchanged, but the failure mode it guards is no longer a *privacy* leak),
   and the link boundary (a general-tier page linking into a
   contemplative-only page gets the ordinary excluded placeholder, like any
   other narrowed link). This is the coherent end state now that "belongs to
   one pair of domains" has become "belongs to the contemplative tier", which
   is exactly what 3 September made true. Cost: an engine PR with tests
   (`test/content-filter.test.js` pins the privacy truth table and would be
   rewritten, not deleted).
3. **Make it an ordinary thread.** Only right if the canonical site is meant
   to move to the contemplative tier and become the complete view. That
   reverses a ruling one day old, so it is listed for completeness rather
   than offered.

**Assessment given in chat:** the second is the shape the ladder implies; the
first costs nothing now. An engine change of this kind is second-tier work
under `CLAUDE.md` — propose, not do — so nothing was changed on the first
pass.

## Sixth, same session — comments on the children's tier

Dermot, verbatim, in two messages:

> should I allow or enable giscus comments on the child reader tier?

> the contemplative tiers use church-space comments, the young adult and
> general tiers share the same comments pool

A question, answered in chat as an assessment; recorded because the answer
is a live-domain change if he wants one. The second message states the
comments architecture, and the registry agrees with it exactly
(`lib/editions.js`, `src/_data/giscus.js`): the three contemplative editions
carry `giscusProfile: "church-space"` (the Communion's board,
`Star-Rangers/churchspace-site-comments`); every other edition falls through
to the default profile (`Star-Rangers/sciencefiction-site-comments`), so the
young-adult and general tiers share one pool.

### What the registry does today, measured

**The children's tier is already in the shared pool, with comments on.** The
`pets` entry sets neither `commentsEnabled` nor `giscusProfile`, so it
inherits the default edition's `commentsEnabled: true` and the default board.
Two consequences follow from how giscus maps discussions: a chapter's thread
is keyed by its permanent `comment_id`, so the discussion under a Season 2
chapter on undercover-pets.com **is the same discussion** as under that
chapter on fianilchruinne.com or starquest.site — adult readers' comments on
the pet chapters appear on the children's site, and vice versa. Non-chapter
pages map by pathname, which is the same across domains too. Nothing about
this was decided; it is what the default does when an entry says nothing.

### What bears on the answer

- **Posting needs a GitHub account.** giscus signs a commenter in through
  GitHub, whose terms require a user to be at least 13; Ireland's digital age
  of consent under GDPR is 16. A child in the tier's readership cannot post,
  and should not be invited to. What the widget offers a child is a place to
  *read* an adult discussion under a story written for them.
- **A separate children's board does not change that.** A new profile and
  repo would isolate the pool (a parent or teacher could post there), at the
  cost of a second board to watch, and the reader profile's rule that the
  children's domain carries no cross-domain link a child cannot judge
  (`edition-reader-profiles.md`, `excludedNotice`) points the same way for a
  comment box.
- **Turning it off costs nothing that exists.** The pets edition has no
  standing discussion of its own to lose; `commentsEnabled: false` is one
  line in the `pets` entry, the shape the sample template already shows.

### Three shapes, put as choices

1. **Off on the children's tier** — `commentsEnabled: false` on the `pets`
   entry. The widget disappears from undercover-pets.com; the same chapters
   keep their discussions on every other domain. **Recommended.**
2. **A children's board of its own** — a third giscus profile and repo,
   isolated from the adult pool. Keeps a comment box for parents and
   teachers; adds a board to moderate; still cannot be used by the reader it
   is for.
3. **Leave it** — shared pool, comments on, as it stands today by default
   rather than by decision.

**RULED the same day — "turn off comments on the children's tier."** The
first shape. Realized as `commentsEnabled: false` on the `pets` entry in
`lib/editions.js`, which `scripts/resolve-edition.js` turns into
`COMMENTS_ENABLED=false` for the undercover-pets.com deploy and
`.eleventy.js` reads to drop the widget. The chapters keep their discussions
on every other domain. One caveat, since `deploy.conf` still wins wherever it
sets a value: the pets clone's own `deploy.conf` must not set
`COMMENTS_ENABLED=true` explicitly, or the server would override the registry
— the deploy log prints each key's provenance, so the next deploy shows which
won.

## Seventh, same session — should the contemplative tier see the shared pool?

Dermot, verbatim:

> Should the contemplative tier be able to view comments from the other
> shared pool?

A question, answered in chat as an assessment; recorded because every answer
but the status quo is an engine change.

### What the site does today, measured

**A board is chosen per build, and a page shows one discussion.**
`GISCUS_PROFILE` selects one comments repo for the whole build
(`src/_data/giscus.js`), and `base.njk` embeds one widget per page keyed by
the chapter's `comment_id` (or the pathname). The three contemplative
editions carry the Communion's board. So since the 3 September ladder gave
them the whole main sequence, a Season 1 chapter on fellowshipoflight.org
shows the **Communion board's** thread for that chapter — a second, separate
conversation from the one the same chapter carries on fianilchruinne.com and
starquest.site — and the shared pool's talk is invisible from the
contemplative doors. Before the ladder this split had nothing to bite on: the
contemplative editions carried only church-space material, and the Communion
board was the whole of what they showed. Nothing about it was decided; it is
what one-board-per-build does once a build carries two readerships' pages.

### Three shapes, put as choices

1. **Pick the board per page, not per build.** A page in the church-space
   thread keeps the Communion's board; every other page on a contemplative
   edition uses the shared pool. The shared chapters then carry one
   conversation across all three tiers that show them, and the overlay keeps
   its own room. Engine work: `giscus.js` exposes both registered profiles,
   `base.njk` picks one by `gatedThreadForPage`, the per-domain
   `GISCUS_PROFILE` becomes the *thread's* board rather than the build's.
   Any thread already opened on the Communion board for a main-sequence
   chapter since 3 September would be orphaned — likely none exist yet, and
   the repo is inspectable before the switch. **Recommended:** it makes "the
   young adult and general tiers share the same pool" true of the pages,
   which is what the sentence means.
2. **Keep one board per edition** — the status quo. Contemplative readers
   hold their own conversation about the shared chapters, separate from the
   pool; two threads per chapter; the pool stays invisible from those doors.
   Costs nothing now and is a defensible reading of "a contemplative site":
   the same story, read among the same company.
3. **One pool for everything** — the contemplative editions switch to the
   default board. Puts the devotional overlay's discussion in the public
   repo the main site reads, which is the thing the Communion board was
   created to avoid. Listed, not offered.

## Eighth, same session — what the tiers are, and are not

Dermot, verbatim:

> the difference between reading tiers is the reading level, choice of

## Ninth, same session — moderation of comments a child might find

Dermot, verbatim:

> the comments should be moderated or hidden until approved if I cannot
> guaranteed their suitability for a child who discovers the side my
> accident - but the GitHub login requirement should help with that

("the side my accident" read as *the site by accident*.) A direction with a
condition in it, answered in chat as an assessment; the honest measurement
first.

### What giscus can and cannot do

- **Pre-approval does not exist in giscus.** It renders GitHub Discussions
  live: a comment is public the moment it is posted, on the site and in the
  Discussions repo. There is no hold-for-review queue in Discussions either.
  Moderation is after the fact — delete, minimise, lock, block — by anyone
  with write access to the comments repo, from GitHub.
- **The login requirement does the most work, as he says.** Posting needs a
  GitHub account (13 or over by GitHub's terms), the account is public and
  attributable, and the comments repos are public with a visible owner.
  Drive-by abuse is rare on that footing; the risk is a real reader posting
  something unsuitable, which is a moderation problem not a gate problem.
- **What is already in place:** the children's tier renders no widget at
  all (sixth ruling), so the accidental child reader on undercover-pets.com
  sees no comments; the other domains carry the pool. He owns both comments
  repos and can act on anything within minutes of a notification.

### Three shapes, put as choices

1. **Notifications plus fast after-the-fact moderation, stated on the
   page.** Watch both comments repos for all activity (GitHub → Watch → All
   Activity), so every new discussion and comment reaches his inbox; add
   the repos' code of conduct and a one-line moderation note under the
   *Discussion* heading ("comments are moderated; anything unsuitable is
   removed"). No engine change beyond the note. **Recommended** as the
   floor: it is what "moderated" can mean on this stack, and it is the part
   the login requirement does not already cover.
2. **Collapse the discussion by default.** Render the widget inside a
   closed `<details>` ("Show discussion") on every domain, so no comment is
   on the page until a reader asks for it. Not moderation — hidden until
   *opened*, not until *approved* — but it keeps an accidental reader from
   meeting a comment they did not go looking for. Cheap; composes with the
   first.
3. **Interaction limits on the comments repos.** GitHub can restrict who
   may comment (existing users, prior contributors, or collaborators only)
   for up to six months at a time, which is the nearest thing to a gate
   Discussions offers. Blunt: it also locks out the readers he wants, and
   it expires.

Listed and not offered: a comments system with a real approval queue, which
means a server or a hosted service holding reader state — the one thing the
site's no-accounts rule (4 August) puts out of scope, and the reason comments
live in GitHub's account system in the first place.

**RULED the same day — "options 1 and 2."** Both, realized together:

- **Watch.** His GitHub account now watches both comments repos for all
  activity (`subscribed: true, ignored: false` on
  `Star-Rangers/sciencefiction-site-comments` and
  `Star-Rangers/churchspace-site-comments`, set through the REST
  subscription endpoint under his `gh` login and read back to confirm).
  Every new discussion and comment reaches his inbox. Neither repo carries a
  code of conduct file; noted, not added — a policy document is his to
  write.
- **The note.** Under the *Discussion* heading on every page that carries a
  widget: *"Comments are read after they are posted and anything unsuitable
  is removed. Posting needs a GitHub account; reading needs nothing."* Says
  what moderation means here and claims no more.
- **Collapsed by default.** The widget sits inside a closed `<details>`
  ("Show discussion") with `data-loading="lazy"`, so nothing loads and
  nothing is on the page until a reader opens it. The heading stays outside
  so the section is still announced. Styled in `main.css` with palette
  tokens only and carried into every theme by `generate-themes`; the
  contrast check's one failure that day (`default`, a missing
  `--status-active` token) predates the change and is filed separately.
